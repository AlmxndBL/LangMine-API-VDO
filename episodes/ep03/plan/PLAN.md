## 1. สถานะและหลักการใช้เอกสาร

- **W3:** คงหัวข้อ Streaming API (SSE) ตามที่ได้รับอนุมัติ และปรับขอบเขต/คำกล่าวให้ตรงตามหลักฐาน snapshot ใน workspace
- **W4:** ทบทวน SCRIPT, STORYBOARD และ CATALOG ให้สอดคล้องกับขอบเขตใหม่ ไม่ใช้ข้อความรับประกันความเร็วหรือตัวเลขวัดเวลาจำลอง
- **W5:** ตรวจสอบภาพ UI ตัวแทนให้มีป้าย "ภาพจำลอง" ชัดเจน และระบุสถานะ Voice Audition ว่ายังรอการคัดเลือก (pending)

### การแยกชั้นสถานะข้อมูล
- **Documented:** อ้างอิงจาก `langmind-api.md` ส่วนต้นฉบับ ได้แก่ Endpoint `POST /chat/message`, ลำดับ Event (`message_start` ➜ `message` ➜ `citations` ถ้ามี ➜ `message_end`), การมี usage และ answer ฉบับเต็มใน `message_end`, และข้อกำหนดความปลอดภัยที่ต้องเก็บ API Key ไว้ที่เซิร์ฟเวอร์
- **Illustrative:** หน้าจอแชทจำลอง, ข้อความคำถาม-คำตอบตัวอย่าง, แผนผังท่อส่งข้อมูล และโค้ดตัวอย่าง เป็นการจำลองเพื่ออธิบายกลไก ไม่ใช่ผลการเรียก API จริง
- **Unknown:** ความเร็ว Time-To-First-Token (TTFT), เวลาในการประมวลผลจริงของแต่ละโมเดล, ประสบการณ์บนเครือข่ายจริง ไม่มีตัวเลขผลวัดในเอกสารนี้

## 2. ผู้ชมและคำถามหลัก (Audience & Core Question)

- **ผู้ชม:** Developer ที่กำลังพัฒนาฟีเจอร์แชทในแอปพลิเคชัน และต้องการเข้าใจว่าการรับข้อมูลแบบสตรีมมิ่งเปลี่ยนวิธีการรับและแสดงผลคำตอบอย่างไร
- **คำถามหลัก:** **เมื่อใช้ SSE ฝั่งแอปได้รับข้อมูลแบบไหน และต้องทำอะไรเพื่อแสดงคำตอบที่ทยอยมา โดยไม่เปิดเผย API Key?**

## 3. ขอบเขตคำตอบและสิ่งที่ไม่กล่าวอ้าง (Scope & Boundaries)

| หัวข้อ | รายละเอียดตามหลักฐาน |
|---|---|
| **LangMind API รับหน้าที่อะไร (Documented)** | • ให้บริการ `POST /chat/message` ส่งข้อมูลแบบ Server-Sent Events (SSE)<br>• ส่ง Event ตามลำดับ: `message_start` ➜ `message` (chunks) ➜ `citations` (ถ้ามี) ➜ `message_end`<br>• `message_end` จะแนบ answer ฉบับเต็มและ token usage มาด้วย (หากขาด terminal event ห้ามกล่าวว่าคำตอบสมบูรณ์แล้ว) |
| **สิ่งที่แอปพลิเคชันต้องทำเอง** | • Backend/Server ของแอปต้องเป็นผู้เก็บ API Key และส่งคำขอไปยัง LangMind<br>• อ่านและ Parse Event Stream จาก LangMind<br>• ส่งต่อข้อมูลที่เหมาะสมไปให้ Client/UI นำไปทยอยแสดงผล<br>• จัดการสถานะการโหลดและข้อผิดพลาด<br>• ตัดสินใจว่าจะนำ `citations` ไปแสดงผลอย่างไร (ไม่เก็บ secret key ไว้บน browser) |
| **ขอบเขตตัวอย่างที่ใช้** | • ใช้เหตุการณ์ถามคำถาม 1 ครั้งในแชทจำลอง เพื่อเปรียบเทียบการรอคำตอบทั้งก้อนกับการทยอยแสดงข้อมูล<br>• หลีกเลี่ยงการสร้างชื่อร้านค้า นโยบาย หรือคำตอบที่ดูเหมือนข้อมูลจริงหากไม่จำเป็น |
| **สิ่งที่ไม่กล่าวอ้าง (Non-Claims)** | • **ไม่กำหนดเวลารอ 5–10 วินาที** หรือใส่ตัวเลขนับเวลาเชิงผลวัด<br>• **ไม่รับประกันว่าเริ่มแสดงผล "ทันที" หรือ "ทันใจ"** (ใช้คำว่า "ทยอยส่ง/ทยอยแสดง" แทน)<br>• **ไม่กล่าวว่า streaming ทำให้โมเดลคิดเร็วขึ้น**<br>• **ไม่รับประกันว่าแชท "ไม่ค้างแน่นอน" หรือ "ลื่นไหลแน่นอน"**<br>• **ไม่เรียกการเรียกแบบเดิม (Blocking) ว่าเป็นเทคโนโลยีเก่าหรือไม่ดี** แต่ให้เรียกตามลักษณะคือ "รับผลครบก่อนแสดง" VS "ทยอยรับและแสดง" |
| **Unknown** | Latency, TTFT และประสบการณ์จริงขึ้นกับโมเดล คำขอ เครือข่าย และการพัฒนาของแต่ละระบบ ไม่มีตัวเลขสมรรถนะยืนยันในเอกสารนี้ |

## 4. โครง Beats สำหรับส่งต่อ W4

| Beat | หน้าที่ของภาพ (Visual) | หน้าที่เสียง (Voiceover) | ข้อความเน้น/ซับ (Text & Subtitle) |
|---|---|---|---|
| **1. อาการรอ** | ภาพจำลองหน้าจอแชทที่ยังไม่มีคำตอบ พร้อมสถานะรอโหลด โดยไม่มีตัวเลขเวลาเชิงผลวัด | ตั้งคำถามจากประสบการณ์ของผู้ใช้เมื่อรอข้อมูล | ซับ: *"หน้าจอยังรอคำตอบ"*<br>ป้าย: `[ภาพจำลอง]` `สถานะ: กำลังรอการตอบกลับ` |
| **2. สองรูปแบบการส่ง** | ภาพเปรียบเทียบคำตอบที่แสดงหลังได้รับครบทั้งก้อน กับข้อความที่ทยอยปรากฏ ระบุว่าเป็นการอธิบายรูปแบบการแสดงผล | อธิบายความต่างระหว่างการรอรับผลครบ กับการรับแบบสตรีมมิ่ง โดยไม่เรียกรูปแบบใดว่าเก่า | ซับ: *"รับผลครบก่อนแสดง"* เทียบกับ *"ทยอยรับและแสดง"*<br>ป้าย: `รับผลครบก่อนแสดง` / `ทยอยรับและแสดง` |
| **3. SSE event flow** | แผนภาพแสดงเส้นทาง: LangMind API ➜ Server ของแอป ➜ Client UI พร้อมกล่อง Event ตามลำดับที่ snapshot ระบุ | ไล่เรียงลำดับ `message_start` ➜ `message` ➜ `citations` (ถ้ามี) ➜ `message_end` | ใช้ชื่อ Event ตามต้นฉบับ อธิบายว่า citations อาจมีหรือไม่มีก็ได้ |
| **4. หน้าที่ของ Developer** | แผนภาพ Backend ของแอปถือ API Key, ทำหน้าที่รับและ parse stream แล้วส่งต่อข้อมูลที่เหมาะสมให้หน้าบ้าน | อธิบายขอบเขตงานของ API เทียบกับงานที่ฝั่งแอปต้องพัฒนาเอง ย้ำการเก็บ Key ที่ Server | ซับ: *"เก็บ API Key ฝั่ง server"*<br>ป้าย: `Backend API Client` / `UI State Parser` |
| **5. สรุป** | แผนผังสรุปย้อน flow สั้น ๆ ตั้งแต่คำขอวิ่งไปจนถึง terminal event | สรุปสิ่งที่ต้องทำและความสำคัญของ terminal event | ซับ: *"แสดงข้อมูลที่ได้รับ — จบเมื่อได้รับ message_end"* |
