## 1. คำแนะนำหัวข้อสำหรับ EP03 (Topic Recommendations)

ตามลำดับการเรียนรู้ของ Developer ต่อจาก EP01 (ปูพื้นฐานว่า API คืออะไร และทดลองส่งคำถามแรก) ขอเสนอแนะ 3 หัวข้อดังนี้:

| ลำดับ | หัวข้อที่แนะนำ | Use Case / ปัญหาที่แก้ | Endpoint อ้างอิงจากคู่มือ | ทำไมถึงเหมาะเป็น EP03 |
|---|---|---|---|---|
| **ตัวเลือกที่ 1 (แนะนำ)** | **ตอบทันใจ ไม่ต้องรอโหลด: ทำระบบแชทแบบ Real-time ด้วย Streaming API (SSE)** | ปัญหา UX แชทบอท: ผู้ใช้ถามคำถามยาวแล้วจอนิ่งไป 5–10 วินาทีจนนึกว่าแอปค้าง เปลี่ยนมาเป็นให้ AI ทยอยพิมพ์คำตอบออกมาทีละคำ | `POST /chat/message` (Server-Sent Events) | **เป็นจุดเปลี่ยนสำคัญด้าน UX ของแอป AI ทุกตัว** ต่อเนื่องจาก EP01 ที่อธิบายแบบ Blocking ได้อย่างเป็นธรรมชาติ เห็นผลลัพธ์ภาพเคลื่อนไหวชัดเจน |
| **ตัวเลือกที่ 2** | **คุยต่อเนื่องไม่มีลืม: จัดการ Memory & Session ด้วย Conversation ID** | ปัญหาถามคำถามต่อเนื่องแล้ว AI ลืมเรื่องก่อนหน้า (เช่น "แล้วราคาเท่าไหร่" แต่ AI ไม่รู้ว่าพูดถึงสินค้าตัวไหน) | `GET/PATCH /chat/conversations`, ส่ง `conversation_id` | ตอบโจทย์คนที่อยากสร้างผู้ช่วยที่สนทนายาว ๆ และแยกผู้ใช้แต่ละคนออกจากกัน |
| **ตัวเลือกที่ 3** | **ส่งภาพให้ AI วิเคราะห์: อัปโหลดสลิป/เอกสารด้วย Attachments API** | ปัญหาบอทรับได้แต่ข้อความ ลูกค้าส่งรูปสลิปหรือรูปสินค้าแล้วบอทอ่านไม่ออก | `POST /v1/attachments/upload` + `attachment_ids` | ขยายขอบเขตจากข้อความสู่ Multimodal แต่ต้องมีขั้นตอนการอัปโหลดไฟล์เพิ่ม |

> **ข้อเสนอแนะ:** เลือก **ตัวเลือกที่ 1 (Streaming API via SSE)** เป็นแกนหลักของ EP03 เพราะเป็นฟีเจอร์ที่ Developer ทุกคนที่สร้างแชทบอทจำเป็นต้องใช้ และมีภาพเปรียบเทียบ UX (ค้าง vs ลื่นไหล) ที่เข้าใจง่ายและดึงดูดสายตาอย่างยิ่ง ด้านล่างคือรายละเอียดการวางแผน W3 สำหรับตัวเลือกนี้

## 2. การออกแบบเรื่องจากมุมคนดู (W3 Story Design)

### 2.1 โจทย์ของคนดู
- **ใครดู:** Developer, Maker หรือผู้สนใจสร้างแอป AI ที่เคยเรียก API แบบธรรมดา (Blocking) แล้วเจอปัญหาเรื่องความหน่วง (Latency)
- **จุดติดขัด (Pain Point):** เมื่อคำตอบของ AI มีขนาดยาว หรือต้องใช้เวลาคิด หน้าจอจะหมุนติ้ว (Loading Spinner) นานหลายวินาที ผู้ใช้มักคิดว่าระบบล่มหรือกดรีเฟรชหน้าจอทิ้ง
- **ทำไมต้องดูคลิปนี้:** เพื่อเข้าใจว่าทำไม ChatGPT หรือแชทบอทสมัยใหม่ถึง "พิมพ์ตอบออกมาทีละคำ" และ LangMind API มีช่องทางให้แอปทำแบบนั้นได้อย่างไรโดยไม่ต้องสร้างระบบ WebSocket ซับซ้อน
- **ดูจบแล้วทำอะไรต่อได้:** สามารถเปลี่ยนโค้ดจากการเรียก `/chat/message/blocking` มาเป็น `/chat/message` พร้อมดักฟัง Event Stream เพื่อนำข้อความทีละคำไปเรนเดอร์บนหน้าจอแอปได้ทันที

## 3. ขอบเขตคำตอบและหลักฐาน (W3 Matrix)

| คำถามร่วม | รายละเอียดสำหรับ EP03 (Streaming Chat) |
|---|---|
| **ใครต้องการทำอะไร** | ผู้ใช้ต้องการถามคำถามกับแชทบอทในแอป และต้องการเห็นข้อความตอบกลับทันทีที่โมเดลเริ่มคิดออก ไม่ต้องรอคำตอบสมบูรณ์ทั้งย่อหน้า |
| **LangMind API รับหน้าที่อะไร** | ให้บริการ Streaming Endpoint ผ่าน HTTP Server-Sent Events (SSE):<br>1. ส่งสัญญาณเริ่มคำตอบ (`message_start`) พร้อม `conversation_id` และ `message_id`<br>2. ทยอยส่งชิ้นส่วนคำตอบ (`message` chunks)<br>3. ส่งแหล่งอ้างอิงถ้ามี (`citations`)<br>4. ส่งสัญญาณจบคำตอบ (`message_end`) พร้อม Usage token ทั้งหมด |
| **แอปพลิเคชันต้องทำอะไรเพิ่ม** | 1. ยิง HTTP POST ไปที่ `/chat/message`<br>2. ใช้ SSE Client (เช่น EventSource หรือ Fetch Stream Reader) รับข้อมูลทีละ Event<br>3. มี State ในฝั่งหน้าบ้านคอยต่อสตริง (String buffer) และอัปเดต UI ให้คำตอบค่อย ๆ พิมพ์ออกมา (Typing effect) |
| **ระดับหลักฐาน (Evidence Status)** | - **Documented:** Endpoint `/chat/message`, โครงสร้าง Event ต่าง ๆ (`message_start`, `message`, `citations`, `message_end`), และข้อกำหนดว่าต้องรอ terminal event ถึงถือว่าสมบูรณ์ (มีในคู่มือ [langmind-api.md](../../langmind-api.md#L39))<br>- **Illustrative:** ตัวอย่างหน้าจอแชทของร้านค้าสมมติ, หน้าต่างโค้ดจำลอง, และข้อความสนทนาตัวอย่าง<br>- **Unknown:** ความเร็วเฉลี่ย Time-To-First-Token (TTFT) จริงของแต่ละโมเดล (ไม่เคลมตัวเลขความเร็วเกินจริง) |
| **สิ่งที่ต้องเห็นในคลิป** | 1. ภาพเปรียบเทียบ 2 จอ: แบบรอ 5 วินาทีแล้วโผล่พรวดเดียว VS แบบทยอยพิมพ์ทันทีในวินาทีแรก<br>2. แผนภาพแสดงท่อส่งข้อมูล Stream (ก้อน Event ลอยมาจากเซิร์ฟเวอร์ทีละแพ็กเก็ต)<br>3. โค้ดตัวอย่างส่วนสำคัญที่รับ Event และนำไปอัปเดตหน้าจอ |

## 4. โครงซีนคร่าว ๆ (High-Level Beats)

| ซีน / จังหวะ | หน้าที่ของเสียง (Voiceover) | หน้าที่ของภาพ (Visual) | หน้าที่ของข้อความ/ซับ (Text & Subtitle) |
|---|---|---|---|
| **Beat 1: ปัญหาของคนรอ** (ประมาณ 10-15s) | เล่าถึงความรู้สึกของผู้ใช้เวลากดส่งข้อความในแชทบอท แล้วต้องนั่งจ้องหน้าจอนิ่ง ๆ รอหมุนวน | หน้าจอแชทจำลอง มี Loading spinner หมุนค้าง นาฬิกานับเวลา 1..2..3.. วินาที ตัวละครหุ่นยนต์ทำท่ารอคอยอย่างกระวนกระวาย | ซับ: *"เคยเจอปัญหานี้ไหมครับ? พิมพ์ถาม AI ไปแล้ว ต้องนั่งรอหน้าจอค้างอยู่หลายวินาที"*<br>ป้ายเน้น: `Loading... (5s)` |
| **Beat 2: ทำไมถึงเป็นแบบนั้น (Blocking)** (ประมาณ 15-20s) | อธิบายว่าการเรียก API แบบปกติ (Blocking) เซิร์ฟเวอร์ต้องรอให้ AI คิดคำตอบจบครบ 100% ถึงจะส่งคำตอบกลับมาทั้งก้อน | แผนภาพแสดง Request วิ่งไป LangMind แล้วฝั่งแอปถูกล็อก (Blocked) รอกล่องคำตอบขนาดใหญ่ประกอบเสร็จถึงวิ่งกลับมา | ซับ: *"เพราะระบบแบบเดิม ต้องรอให้คิดคำตอบเสร็จทั้งหมด ถึงจะส่งกลับมาได้"*<br>ป้ายเน้น: `Blocking Request = รอจนจบ` |
| **Beat 3: ทางออกด้วย Streaming (SSE)** (ประมาณ 25-30s) | แนะนำ `/chat/message` ของ LangMind ที่เปลี่ยนมาใช้เทคโนโลยี Server-Sent Events (SSE) คิดได้คำไหน ส่งคำนั้นทันที | หน้าจอแบ่งครึ่งเปรียบเทียบ ด้านหนึ่งยังหมุนติ้ว อีกด้านเริ่มมีตัวอักษรพิมพ์วิ่งออกมาทีละคำทันทีที่วินาทีแรก ตัวละครหุ่นยนต์ชี้นิ้วชื่นชม | ซับ: *"แต่ด้วย Streaming API ของ LangMind ทันทีที่ AI คิดคำแรกได้ ข้อความจะเริ่มทยอยส่งมาทันที"*<br>ป้ายเน้น: `Server-Sent Events (SSE)` |
| **Beat 4: เบื้องหลังการทำงาน (The 3 Events)** (ประมาณ 25-30s) | อธิบายสเต็ปข้อมูลที่ไหลผ่านท่อ: มีสัญญาณเริ่มต้น ข้อความแต่ละก้อน และสัญญาณจบคำตอบ | กล่องข้อความ Event Stream วิ่งไหลเป็นท่อ: `message_start` ➜ ก้อน `message` รัว ๆ ➜ จบที่ `message_end` | ซับ: *"ข้อมูลจะส่งมาเป็นชุดเหตุการณ์ ตั้งแต่เริ่ม ทยอยส่งชิ้นส่วนข้อความ จนถึงสัญญาณยืนยันว่าจบคำตอบ"*<br>ป้ายเน้น: `message_start` / `message` / `message_end` |
| **Beat 5: สรุปและการนำไปใช้** (ประมาณ 15-20s) | สรุปว่าแอปแค่เปลี่ยน Endpoint และดักรับสตรีม ก็เปลี่ยนประสบการณ์ผู้ใช้ให้รู้สึกลื่นไหลทันที | หน้าจอสรุปโค้ดบรรทัดสำคัญ และหน้าจอแชทที่ตอบคำถามเสร็จสมบูรณ์ โลโก้ LangMind และตัวละครหุ่นยนต์โบกมือพร้อมข้อความเชิญชวนไปลอง | ซับ: *"เพียงเท่านี้ แชทบอทของคุณก็จะตอบสนองได้รวดเร็ว ลื่นไหล เหมือนคุยกับคนจริง ๆ"*<br>ป้ายเน้น: `POST /chat/message` |

## 5. การจับคู่ Motion Catalog เบื้องต้น (Catalog Mapping)

คัดเลือกรูปแบบ Motion จาก [docs/CATALOG_USAGE_MAP.md](../../docs/CATALOG_USAGE_MAP.md) ให้ตรงตามหน้าที่ของแต่ละซีน:

1. **Beat 1 & 2:**
   - ใช้ `layout: split` หรือ `card: spotlight` สำหรับวางกรอบแชทมือถือ
   - ใช้ `status: pulse` หรือตัวหมุน Loading เพื่อแสดงสถานะรอคอย
2. **Beat 3 (เปรียบเทียบ):**
   - ใช้ `layout: split` ซ้าย-ขวา เปรียบเทียบ Blocking vs Streaming พร้อมป้ายกำกับ
   - ใช้เอฟเฟกต์จำลอง Typing Cursor บนข้อความฝั่ง Streaming
3. **Beat 4 (ท่อส่งข้อมูล):**
   - ใช้ `diagram: flow` หรือการเลื่อนของ Data Packet เพื่อให้เห็นก้อน Event วิ่งจากขวา (API Server) ไปซ้าย (Mobile App)
4. **Beat 5 (ปิดท้าย):**
   - ใช้ `card: hero` สำหรับสรุป Key Takeaway และปุ่ม Call-to-Action
