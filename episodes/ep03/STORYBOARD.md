### ซีนที่ 2: สองรูปแบบการส่งข้อมูล (Scene 02: Delivery Modes)
- **Scene ID:** `SC02-MODES`
- **เป้าหมาย:** เปรียบเทียบระหว่าง "รับผลครบก่อนแสดง" กับ "ทยอยรับและแสดง" โดยไม่เรียกแบบใดว่าเก่าหรือรับประกันความเร็ว
- **Beats:**
  - *Beat 2.1:* หน้าจอจัดวางเปรียบเทียบ 2 รูปแบบ
    - ฝั่งหนึ่ง: การ์ด `รูปแบบรับผลครบก่อนแสดง` (Blocking) รอจนเสร็จทั้งชุดจึงปรากฏ
    - อีกฝั่งหนึ่ง: การ์ด `รูปแบบทยอยรับและแสดง` (Streaming ผ่าน `POST /chat/message`) ข้อมูลทยอยปรากฏทีละชุด
  - *Beat 2.2:* หุ่นยนต์ผายมือนำสายตาเพื่อชี้ให้เห็นความแตกต่างของรูปแบบการรับส่งข้อมูล
- **Composition & Focus:**
  - เลย์เอาต์เปรียบเทียบแบบแบ่งสัดส่วน
  - ฝั่งรับผลครบ: แสดงกล่องข้อความที่ปรากฏขึ้นมาเมื่อสมบูรณ์
  - ฝั่งทยอยรับ: แสดงกล่องข้อความที่ทยอยแสดงชิ้นส่วนข้อมูลที่ส่งมาเป็นระยะ
- **Character (หุ่นยนต์):**
  - ไฟล์: `shared/assets/characters/robot/05-point-up.png`
  - บทบาท: ยืนนำสายตาคนดูเพื่อเปรียบเทียบการทำงานของสองระบบ
- **Narration & Subtitle:**
  - บทพากย์: *"ใน LangMind API มีทางเลือกการเชื่อมต่อสองรูปแบบหลัก รูปแบบแรกคือการรับผลครบก่อนแสดง และอีกรูปแบบหนึ่งคือการใช้ Streaming API ผ่าน Endpoint chat/message เมื่อใช้ Streaming ระบบจะเริ่มทยอยส่งชิ้นส่วนข้อความออกมาเป็นระยะ ทำให้ฝั่งแอปพลิเคชันสามารถนำข้อมูลที่เริ่มได้รับไปทยอยแสดงผลบนหน้าจอได้"*
  - ข้อความเน้นบนจอ: `POST /chat/message` / `รูปแบบ: รับผลครบก่อนแสดง` / `รูปแบบ: ทยอยรับและแสดง (SSE)`
- **Motion:**
  - การทยอยแสดงข้อความตามกลุ่มข้อมูล (Chunk reveal) ในฝั่ง Streaming
- **Evidence:** Documented ([langmind-api.md](../../langmind-api.md#L31)) + Illustrative Comparison
- **Exit & ส่งต่อ:** ภาพเชื่อมต่อไปยังแผนผังแสดงรายละเอียดของชุด Event ในซีนที่ 3

### ซีนที่ 3: ลำดับ Event ในท่อ SSE (Scene 03: Event Flow)
- **Scene ID:** `SC03-STREAM-FLOW`
- **เป้าหมาย:** อธิบายลำดับของ Server-Sent Events ตามที่ระบุใน snapshot อย่างถูกต้อง ครบถ้วน
- **Beats:**
  - *Beat 3.1:* ปรากฏเส้นทางเชื่อมต่อ: LangMind API Server ➜ Backend ของแอป ➜ Client UI
  - *Beat 3.2:* กล่อง Event วิ่งมาตามลำดับ:
    1. `event: message_start` (ส่ง conversation_id และ message_id ยืนยันเริ่มต้น)
    2. `event: message` (ส่ง chunk ชิ้นส่วนข้อความคำตอบ)
    3. `event: citations` (ส่งแหล่งอ้างอิงเอกสาร หากมี)
    4. `event: message_end` (ส่งคำตอบฉบับสมบูรณ์ + สรุป Token Usage)
  - *Beat 3.3:* เน้นย้ำว่าต้องได้รับ `message_end` ซึ่งเป็น terminal event จึงจะถือว่าคำตอบเสร็จสมบูรณ์
- **Composition & Focus:**
  - แผนภาพท่อข้อมูลแนวนอน จัดเรียงลำดับ Event ชัดเจน
  - มีป้ายกำกับและสีแยกประเภท Event ชัดเจน
- **Character (หุ่นยนต์):**
  - ไฟล์: `shared/assets/characters/robot/20-laptop.png`
  - บทบาท: หุ่นยนต์สังเกตการณ์อยู่ที่ฝั่ง Backend คอยตรวจสอบลำดับของ Event
- **Narration & Subtitle:**
  - บทพากย์: *"ข้อมูลที่สตรีมผ่าน Server-Sent Events จะส่งมาเป็นชุดเหตุการณ์ตามลำดับ เริ่มจาก message_start ซึ่งส่งรหัสบทสนทนาและข้อความมาเพื่อยืนยันการเริ่มต้น จากนั้นตามด้วย event ชนิด message ซึ่งจะทยอยส่งชิ้นส่วนข้อความหรือ chunk เข้ามา และอาจมี event citations ส่งมาประกอบหากมีการอ้างอิงเอกสาร และสำคัญที่สุดคือ event สุดท้าย message_end ที่จะส่งคำตอบฉบับสมบูรณ์พร้อมสรุปจำนวน Token มาให้ ซึ่งเราต้องรอจนได้รับ event นี้ จึงจะถือว่าคำตอบสมบูรณ์แล้ว"*
  - ข้อความเน้นบนจอ: `1. message_start` ➜ `2. message` ➜ `[citations (ถ้ามี)]` ➜ `3. message_end (Terminal)`
- **Motion:**
  - กล่อง Event เลื่อนตามท่อจากขวาไปซ้ายตามลำดับที่เกิดขึ้นจริง
- **Evidence:** Documented SSE Contract ใน [langmind-api.md](../../langmind-api.md#L39)
- **Exit & ส่งต่อ:** ส่งต่อไปยังหน้าที่เฉพาะของ Developer ในการจัดการ Event เหล่านี้ในซีนที่ 4

### ซีนที่ 4: หน้าที่ของ Developer และระบบฝั่งแอป (Scene 04: Developer Responsibilities)
- **Scene ID:** `SC04-DEV-ROLE`
- **เป้าหมาย:** แยกขอบเขตหน้าที่อย่างชัดเจน: Backend เก็บ Key และ parse stream ส่วน Client แสดงผล; API ไม่ได้จัด UI ให้
- **Beats:**
  - *Beat 4.1:* แผนภาพสถาปัตยกรรมแสดง Server ของแอปเป็นตัวกลางเก็บ API Key ป้องกันความปลอดภัย
  - *Beat 4.2:* แสดงการทำงานของ Backend: รับ Event Stream ➜ ถอดรหัส (Parse) ➜ ส่งต่อเฉพาะข้อความให้ Client
  - *Beat 4.3:* Client ทำหน้าที่รับข้อความไปทยอยอัปเดต State บนหน้าจอ
- **Composition & Focus:**
  - กรอบ Backend เน้นไอคอนกุญแจความปลอดภัย (Server Secret Store)
  - กรอบ Client เน้นการอัปเดต UI State
- **Character (หุ่นยนต์):**
  - ไฟล์: `shared/assets/characters/robot/39-tiptoe.png`
  - บทบาท: ชี้ไปที่กล่อง Backend เพื่อย้ำเรื่องความปลอดภัยในการเก็บ Key
- **Narration & Subtitle:**
  - บทพากย์: *"ในฝั่งการพัฒนา สิ่งสำคัญคือเราต้องเก็บ API Key ไว้ที่ฝั่งเซิร์ฟเวอร์หรือ Backend ของแอปเราเสมอ ห้ามใส่ไว้ในโค้ดฝั่งหน้าบ้านหรือเบราว์เซอร์เด็ดขาด Backend ของเราจะทำหน้าที่รับและอ่าน Event Stream จาก LangMind แปลงข้อมูล และส่งเฉพาะข้อความที่ต้องการไปยังหน้าบ้าน เพื่อนำไปจัดการสถานะและแสดงผลต่อไป"*
  - ข้อความเน้นบนจอ: `เก็บ API Key ที่ Server เสมอ` / `Backend: Parse Stream` ➜ `Client: จัดการ UI`
- **Motion:**
  - ไฮไลต์การไหลของข้อมูลจาก Backend สู่ Client UI
- **Evidence:** Documented Architecture ([langmind-api.md](../../langmind-api.md#L20))
- **Exit & ส่งต่อ:** รวมองค์ประกอบเพื่อสรุปภาพรวมทั้งหมดในซีนที่ 5

## 2. แบบหน้าจอทุกภาพก่อนเจน (Screen Specs Matrix)

### Screen Spec 1: หน้าจอแชทสถานะรอคำตอบ (Screen ID: `SCR-01-CHAT-LOADING`)
- **การใช้งานในคลิป:** ซีนที่ 1 (Beat 1.1–1.3) และด้านหนึ่งของซีนที่ 2
- **วัตถุประสงค์:** แสดงหน้าจอแชทจำลองที่กำลังรอการตอบกลับจากเซิร์ฟเวอร์ โดยไม่มีตัวเลขเวลานับถอยหลัง
- **เนื้อหาข้อความภาษาไทยจริง:**
  - หัวแอป: `ระบบถาม-ตอบจำลอง`
  - สถานะด้านบน: `สถานะ: กำลังรอการตอบกลับจากระบบ`
  - ฟองคำพูดผู้ใช้ (ขวาบน): *"ขอทราบขั้นตอนการเริ่มต้นใช้งานระบบหน่อยครับ"*
  - พื้นที่รอคำตอบ (ซ้าย): จุดสถานะกำลังประมวลผล (Dots Indicator) พร้อมข้อความ *"กำลังรอข้อมูลชุดสมบูรณ์..."*
  - **ป้ายกำกับมุมล่าง (บังคับมี):** `[ภาพจำลอง: รูปแบบรับผลครบก่อนแสดง]`
- **Layout:** กรอบสมาร์ตโฟนแนวตั้ง สะอาดตา มินิมอล พื้นหลังสีเทาอ่อน `#F8FAFC`
- **สถานะ:** `Waiting State` (ยังไม่มีข้อความคำตอบ)
- **Continuity:** ตำแหน่ง Header Bar, ฟองคำพูดคำถามผู้ใช้, และพื้นที่อินพุตล่าง ต้องตรงกับ `SCR-02` แบบ 1:1
- **ขนาดและ Framing:** สัดส่วน 9:16 (1080×1920)

### Screen Spec 2: หน้าจอแชทกำลังทยอยแสดงผล (Screen ID: `SCR-02-CHAT-STREAMING`)
- **การใช้งานในคลิป:** ซีนที่ 2 (ฝั่ง Streaming) และซีนที่ 4
- **วัตถุประสงค์:** แสดงหน้าจอเดียวกันในรูปแบบที่ชิ้นส่วนข้อความทยอยปรากฏบนหน้าจอ
- **เนื้อหาข้อความภาษาไทยจริง:**
  - หัวแอป: `ระบบถาม-ตอบจำลอง` (ตรงกับ `SCR-01`)
  - สถานะด้านบน: `สถานะ: กำลังทยอยรับข้อมูล (Server-Sent Events)`
  - ฟองคำพูดผู้ใช้: *"ขอทราบขั้นตอนการเริ่มต้นใช้งานระบบหน่อยครับ"* (ตรงกับ `SCR-01` 100%)
  - ฟองคำพูดผู้ช่วย (กำลังทยอยแสดง): *"ขั้นตอนแรกคือการสร้าง API Key จากหน้าจัดการระบบ..."* พร้อมเคอร์เซอร์แสดงตำแหน่งข้อความล่าสุด
  - **ป้ายกำกับมุมล่าง (บังคับมี):** `[ภาพจำลอง: รูปแบบทยอยรับและแสดงผล (SSE)]`
- **Layout:** กรอบและตำแหน่งเหมือน `SCR-01` ทุกประการ เพื่อให้เปรียบเทียบรูปแบบการแสดงผลได้อย่างชัดเจน
- **สถานะ:** `Streaming / Partial Content State`

### Screen Spec 3: แผนภาพลำดับ Event ในท่อ SSE (Screen ID: `SCR-03-SSE-DIAGRAM`)
- **การใช้งานในคลิป:** ซีนที่ 3 (Beat 3.1–3.3)
- **วัตถุประสงค์:** แสดงแผนภาพการไหลของ Event จาก LangMind สู่ Backend และ Client ตาม snapshot
- **เนื้อหาข้อความจริง:**
  - โหนดขวา: `LangMind API Server (POST /chat/message)`
  - โหนดกลาง: `App Backend (Server Secret Store)`
  - โหนดซ้าย: `Client App (UI State)`
  - ลำดับกล่อง Event ในท่อ:
    1. `message_start` (เริ่มสตรีม, ให้ conversation/message ID)
    2. `message` (ชิ้นส่วนข้อความ / chunks)
    3. `citations` (แหล่งอ้างอิงเอกสาร ถ้ามี)
    4. `message_end` (จบคำตอบ, ให้ answer สมบูรณ์และ usage)
- **Layout:** ไดอะแกรม 3 ฝั่งพร้อมท่อข้อมูลแนวนอน มินิมอล พื้นหลังสีเข้มโปร่งแสง

    - ข้อความ: `• จัดการ UI State และทยอยแสดงผล`
    - ข้อความ: `• ห้ามเก็บ API Key ใน Browser`
- **Layout:** แผนผังแบ่ง 2 ระดับอย่างชัดเจน มีไอคอนแม่กุญแจความปลอดภัย
