# ข้อกำหนดการออกแบบเรื่อง Storyboard และ Prompt

เอกสารนี้กำหนดวิธีทำงานสำหรับขั้นถัดไป ไม่ใช่ storyboard ของ EP01 และไม่มีเรื่อง/ซีนใหม่ที่ล็อกแล้ว

## หลักการออกแบบเรื่อง
ก่อนเริ่มระบุผู้ชม ความต้องการ จุดติดขัด เหตุผลในการดู พื้นฐานที่ต้องรู้ คำถามหลัก ขอบเขตคำตอบ และสิ่งที่คนดูนำไปทำต่อได้
ใช้ use case อธิบายขั้นเตรียม การเชื่อม API และการนำผลไปใช้ ไม่ต้องสร้างระบบจริง แยก API capability จากงานของ developer และตรวจหลักฐานก่อนผลิตภาพ
กำหนดความลึกตามสิ่งที่คลิปสัญญากับคนดู โดยใช้คำถามร่วมและระดับรายละเอียดใน [Workflow ส่วน W3](WORKFLOW.md#ขอบเขตตาม-use-case-ใน-w3) ไม่บังคับทุกคลิปมี endpoint โค้ด diagram หรือรายละเอียดระบบเท่ากัน ฟีเจอร์บนหน้าเว็บผลิตภัณฑ์ไม่แทนหลักฐาน API contract
เริ่มจากคนดูและสิ่งที่อยากให้เข้าใจ เลือกประเด็นหลักที่สัมพันธ์กัน ระบุสถานการณ์/คำถาม เหตุการณ์ที่ทำให้เข้าใจ และผลที่นำไปใช้ได้
จัดเนื้อหาโดยเหตุและผล ไม่แบ่งตามรายการความสามารถ API โดยอัตโนมัติ ความยาวและจำนวนซีนตามความจำเป็น ไม่ยึดตัวเลข v3
วางโครงซีนคร่าว ๆ และแบ่งหน้าที่ภาพ/เสียง/ข้อความก่อนเลือก Catalog รายคลิป ไม่ต้องรอสำรวจ Catalog ครบทั้งหมด
ใช้ทะเบียนกลางค้นตัวเลือก ดู preview และทดลองจุดที่ยังไม่แน่ใจก่อนลงรายละเอียด storyboard; เลือกตามหน้าที่ซีน ทำ custom เฉพาะ gap จำเป็น Robot เป็นตัวประกอบที่เลือกหลังทราบหน้าที่ของจังหวะ

## โครงซีนคร่าว ๆ ก่อนเลือก Catalog
| ช่อง | เนื้อหา |
|---|---|
| คำถามคนดู | คนดูสงสัยอะไรในช่วงนี้ |
| ใจความหลัก | หลังช่วงนี้ควรเข้าใจอะไรหนึ่งเรื่อง |
| ภาพ | สิ่งที่ต้องเห็น เช่น ลำดับ ความสัมพันธ์ ความต่าง หรือผลของการกระทำ |
| เสียง | เหตุผล บริบท เงื่อนไข และการเชื่อมความคิดที่ต้องอธิบาย |
| ข้อความ | ชื่อ ป้าย คำสำคัญ ค่าหรือข้อจำกัดที่ต้องเห็นตรง ๆ |
| จุดสนใจและการเปลี่ยนแปลง | มองอะไรก่อน/หลัง อะไรต้องเผย ขยาย เปลี่ยนสถานะ หรืออยู่นิ่ง |
| ความต่อเนื่อง | รับอะไรจากช่วงก่อนและส่งอะไรไปช่วงถัดไป |
| หลักฐาน/สิ่งที่ต้องทดลอง | แหล่งและสถานะ claims รวมจุดที่ sample ต้องตอบ |
ยังไม่ล็อกจำนวนซีน เวลา layout หรือชื่อเอฟเฟกต์ รวมช่วงที่ซ้ำและเติมพื้นฐานจำเป็นก่อนเลือก motion
ใช้ข้อมูลภาพและการเปลี่ยนแปลงค้น Catalog แล้วขยายเป็นรายละเอียดรายซีนด้านล่าง รวมในแผนเดิมได้โดยไม่สร้างเอกสารซ้ำ

## กฎ Storyboard
1. แต่ละ beat ทำให้คนดูเข้าใจเพิ่มหนึ่งเรื่อง ระบุความสงสัยก่อนและความเข้าใจหลัง
2. ระบุเหตุการณ์ที่เห็นได้: ภาพเริ่มต้น → การกระทำ/การเปลี่ยนแปลง → ภาพจบ; “ขึ้นหัวข้อและภาพ” อย่างเดียวไม่พอ
3. แยกหน้าที่ภาพ เสียง ซับ และข้อความเน้น ตรวจความซ้ำเชิงความหมาย ห้ามลดซับที่จำเป็นเพียงเพื่อให้จำนวนคำดูน้อย
4. หนึ่งจุดสนใจหลักต่อ beat ระบุลำดับสายตาและสิ่งที่ย่อ หรี่ หรือออกจากฉาก
5. ตัวละครต้องตั้งคำถาม ชี้ ตอบสนอง เชื่อมประเด็น หรือสรุป เลือก pose ตามบทบาท ไม่บังคับอยู่ทุกเฟรม
6. เปลี่ยน framing ตามข้อมูล ใช้ภาพใกล้เมื่อรายละเอียดสำคัญ ไม่แสดง screenshot เต็มใบซ้ำเพราะมี asset อยู่แล้ว
7. Motion แสดงการเปลี่ยนแปลงหรือพาสายตา ระบุชนิด/จังหวะ ไม่เติมเอฟเฟกต์เพื่อให้ดูขยับ
8. ฉากจบต้องส่งต่อเหตุผลไปฉากถัดไป ตรวจว่าแยกศัพท์ที่ยังไม่จำเป็นออกได้หรือไม่
9. ไม่บังคับจำนวนคำ/เอฟเฟกต์ตายตัว ใช้การอ่านบนมือถือและความเข้าใจเป็นหลัก
10. แยก illustrative กับ observed และห้ามแสดงการทำงานที่เกิน API contract

## รายละเอียดที่ต้องมีต่อซีน
| ช่อง | เนื้อหาที่ต้องระบุ |
|---|---|
| ID / เป้าหมาย | เข้าใจอะไร บทบาทต่อเรื่อง และเวลาโดยประมาณ |
| Beats | แต่ละจังหวะ: เริ่มต้น การกระทำ ผลที่เห็น และระยะเวลาร่าง |
| Composition / focus | ภาพหลัก crop จุดสำคัญ framing ลำดับสายตา พื้นที่ซับ |
| Character | ไฟล์ pose บทบาท ทิศชี้ จุดยืน/ฐาน และจังหวะเข้าออก หรือเหตุผลที่ไม่ใช้ |
| Narration / captions / emphasis | บทพากย์ ซับ คำเน้น แยกชัด พร้อมเหตุผลของข้อความเพิ่มเติม |
| Motion | Catalog ID/ชื่อจริง ชนิด preview reference การปรับและ fallback เฉพาะที่จำเป็น |
| Assets / continuity | ไฟล์ ขนาด สถานะภาพ crop-safe พื้นที่คงเดิม transparency และชิ้นที่แยกขยับ |
| Evidence | documented/observed/illustrative/unknown และ source ของ claims |
| Exit / acceptance | ภาพจบ การส่งต่อฉาก วิธีตรวจความเข้าใจ มือถือ และจุดที่ยังต้องลอง |

ยังไม่สร้าง scene table รายตอนจนมี task ระบุให้ทำ
ก่อน sample ให้มีโครงและรายการ assets ทั้งตอน ลงรายละเอียดตารางนี้ให้ครบช่วง sample และระบุส่วนอื่นที่รอผลทดลอง หลัง sample จึงปรับรายละเอียดส่วนที่เหลือก่อนผลิต ไม่ต้องกรอกเวลาขั้นสุดท้ายทุกซีนล่วงหน้า
การตรวจ API การทดลองสื่อ ลำดับเสียง และเส้นทางย้อนแก้ใช้ [Workflow](WORKFLOW.md) เป็นหลัก W4 ลองอ่านบทร่าง W5 ทดสอบพร้อมเสียงร่าง/ซับ และ W6 ให้เสียงเสถียรก่อนเก็บ timing ละเอียด

## แบบหน้าจอรายภาพก่อนเจน
ทุกภาพหน้าจอที่ปรากฏในคลิปต้องมีแบบ ไม่ใช่เพียงชื่อไฟล์หรือหัวข้อ รวมภาพ insert และภาพ close-up ด้วย หาก crop จาก source เดียวระบุ mapping และ crop ที่ใช้ ไม่ต้องเจนซ้ำ
เก็บแบบไว้กับ storyboard/asset manifest ของตอน ไม่สร้างเอกสารซ้ำเมื่อรวมในไฟล์เดิมได้

| ข้อมูล | สิ่งที่ต้องออกแบบ |
|---|---|
| Screen ID / การใช้ | ID คงที่ ฉาก/beat วัตถุประสงค์ สิ่งที่ต้องเห็น และภาพเดิมที่ reuse |
| เนื้อหา | ข้อความไทยจริงที่ต้องปรากฏ label ปุ่ม คำถาม คำตอบ และป้ายภาพจำลอง ระบุ claims/source ห้ามปล่อยให้ตัวเจนแต่งข้อมูลสำคัญ |
| Layout | โครงพื้นที่ ลำดับชั้น ขนาดสัมพัทธ์ ตำแหน่งจุดสำคัญ ลักษณะหน้าตา; ใช้ wireframe เมื่อข้อความอธิบายยังคลุมเครือ |
| สถานะ | ก่อนกระทำ ระหว่างรอ หลังได้ผล หรือสถานะอื่นเฉพาะที่ใช้จริง ไม่สร้าง error/empty state เผื่อทุกคลิป |
| Continuity | ภาพฐาน/reference ที่ใช้ร่วม geometry สี ฟอนต์ controls และข้อความที่คงเดิม รวมรายการที่อนุญาตให้เปลี่ยนต่อภาพ |
| ขนาดและ framing | ขนาดต้นทาง สัดส่วน ขนาดแสดงสูงสุด พื้นที่ crop/zoom จุดอ่านหลักและบริเวณที่ต้องเผื่อ ไม่อ้างว่าขยายได้ไม่จำกัด |
| Layer / motion | ส่วนใดอยู่ใน raster ส่วนใดแยกเป็น asset และ overlay อธิบาย จุดกด/ไฮไลต์ที่อ้างอิงภาพ และ Catalog ที่ต้องรองรับ |
| Prompt / version | prompt เต็ม reference inputs รุ่น source file และผลเจนที่เลือก ผูกกับ asset ID |
| ผลตรวจ | เทียบแบบ ข้อความไทย อ่านที่มือถือและ crop จริง ความต่อเนื่องระหว่างภาพ ข้อผิดพลาดและรุ่นแก้; ห้ามรับเพียงเพราะเจนครบ |

ลำดับคือ ออกแบบทุกภาพในขอบเขตที่จะผลิต → ตรวจแบบกับ storyboard/motion → เจนตามชุดสถานะ → ตรวจภาพจริงและภาพคู่สถานะ → รับเป็น asset → ประกอบ
ช่วง sample ใช้แบบครบสำหรับภาพใน sample เท่านั้น หลังเรียนรู้จาก sample จึงปรับแบบและเจนส่วนที่เหลือก่อน timeline เต็ม
ภาพจำลองไม่ใช่หน้าจอทางการหรือผลเรียกจริง ไม่สร้าง UI ด้วย HTML ทับภาพที่เจนผิด; ป้าย/ลูกศร/caption อธิบายนอก UI แยกชั้นได้

## โครง Production prompt
ทุก prompt ต้องระบุ source-of-truth และรุ่น ขอบเขตซีน/beat ที่ทำ allowed outputs assets ที่ต้องใช้ motion ที่เลือก ข้อจำกัดสิ่งห้ามสร้าง และเกณฑ์ตรวจ
ระบุว่าอะไรห้ามเปลี่ยนระหว่างภาพสถานะ เช่น geometry ฟอนต์ ตำแหน่ง controls และบริเวณข้อความ ไม่ใช้เพียง “ให้เหมือนเดิม”
แยก prompt เจน asset ออกจาก prompt ประกอบ เก็บข้อความ prompt ฉบับเต็มพร้อม reference inputs ผลลัพธ์จริงและรุ่น ไม่ใช้ generated source filename แทน prompt
คำว่า “น่าดู”, “ตาม reference”, “มีจังหวะ” ต้องมีคุณลักษณะและตัวอย่างที่ตรวจได้กำกับ
ห้ามใช้เงื่อนไขความปลอดภัย/ความถูกต้องจำนวนมากแทนคำสั่งว่าภาพต้องเล่าอะไร

## ตรวจแผนก่อนผลิต
- คนดูมีเหตุผลอะไรที่จะดูต่อ แต่ละช่วงแสดงอะไร เกี่ยวกับขั้นก่อนอย่างไร และจบแล้วเริ่มลงมือจากตรงไหน
- ขอบเขตคำตอบไม่เกินคำถามหลัก และศัพท์ใหม่มีพื้นฐานรองรับ; ทุก claim มี source หรือแสดงสถานะ unknown ไว้ก่อนแก้
- มีแบบหน้าจอครบทุกภาพในขอบเขตที่จะเจน: ก่อน sample ตรวจเฉพาะภาพ sample ส่วนที่เหลือตรวจหลังปรับจากผลทดลองและก่อนเจน; sample ทดสอบความไม่แน่นอนที่ระบุ ไม่ใช่เลือกเฉพาะส่วนที่ทำง่าย
- อ่านเฉพาะช่องภาพ/การกระทำแล้วตามเหตุการณ์หลักได้หรือไม่ รายละเอียดเชิงเทคนิคให้เสียง/ซับช่วยได้
- ฟังบทแล้วดูภาพประกอบชัดขึ้นหรือเพียงอ่านข้อความเดียวกัน
- เปิดเฟรมขนาดมือถือแล้วเห็นจุดหลักโดยไม่ต้องอ่านทุกองค์ประกอบหรือไม่
- ข้อความและ assets แต่ละชิ้นมีหน้าที่หรือไม่; ช่วง hold มีเวลาอ่าน/เหตุผลรองรับหรือไม่
- เปรียบเทียบ reference ด้าน framing เส้น ป้าย ตัวละคร และความสัมพันธ์ของชิ้นงาน แยกจาก technical pass
- ช่วง sample ต้องทดสอบความไม่แน่นอนจริงก่อนผลิตเต็ม ไม่ถือแผนที่กรอกครบว่า visual ผ่าน
